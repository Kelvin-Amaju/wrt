# OrbitQA v0.8 Per-Link Device Matrix Design

## Status
Approved architecture, written specification for implementation review.

## Goal
Replace the v0.7 shared-run model with a per-link, per-device execution matrix where every browser/device instance is an independent work unit with its own browser context, timer, proxy allocation, route verification, interaction lifecycle, logs, and cleanup.

The redesign must also repair the current Smart Interaction shortcomings by introducing a scroll-surface driver and blocker-aware interaction coordinator that work on pages whose main content is not the window scroll surface.

## Non-goals and safety boundaries

OrbitQA remains an authorized QA/testing tool. v0.8 must not add fingerprint spoofing, anti-detection bypasses, stealth identity forgery, or automation that pretends to satisfy CAPTCHA / "I'm not a robot" / human-verification challenges.

The blocker resolver may dismiss the surrounding overlay when a separate safe X/Close/backdrop exists. If a genuine human-verification challenge is the only path forward, OrbitQA records `Human verification requires manual action` and leaves the visible browser available until the work-unit timer expires or the user stops it.

OrbitQA must not intentionally click advertisement CTAs, install/update prompts, checkout/purchase controls, destructive controls, payment fields, password fields, OTP fields, or account-number fields. Ads remain enabled; only page-blocking surfaces are dismissed when a safe dismissal exists.

## Current v0.7 limitation being replaced

Today `QaRunRequest` stores these settings once for the entire run:

- `targetUrls`
- `sessionDurationSeconds`
- `deviceMode`
- `deviceName`
- `browser`
- `sessions`
- `proxySource`
- iOS profile/browser/orientation settings

`buildWorkUnits()` then repeats every target with the same run-level configuration. This makes URLs independent only in name. Device/browser/timer/proxy behavior is still shared at run level.

v0.8 removes that assumption.

# 1. Execution model

## 1.1 Target plans

A run contains one or more `QaTargetPlan` records. Each target has one URL and one or more launch groups.

```ts
export interface QaTargetPlan {
  id: string;
  targetUrl: string;
  groups: QaLaunchGroup[];
}
```

Each target URL is normalized independently. Bare domains are accepted and normalized with `https://` while preserving existing protocol-error behavior for unsupported schemes.

Maximums for v0.8:

- 20 target plans per run.
- 12 launch groups per target.
- 50 total generated work units per run.
- Global active concurrency remains 1-5 in v0.8 for stability; extra work units queue.

## 1.2 Launch groups

A launch group describes how many independent work units to create for one device/browser configuration.

```ts
export type QaExecutionKind =
  | 'desktop'
  | 'android-emulation'
  | 'android-avd'
  | 'ios-emulation'
  | 'real-ios';

export interface QaLaunchGroup {
  id: string;
  label?: string;
  executionKind: QaExecutionKind;
  browser: QaBrowser | 'chrome-android' | 'safari-ios' | 'chrome-ios';
  deviceProfile?: string;
  androidAvdName?: string;
  realIos?: RealIosCapabilitySelection;
  orientation?: 'portrait' | 'landscape';
  locale?: string;
  timezoneId?: string;
  instances: number;
  sessionDurationSeconds: number;
  proxySource: ProxySource;
  allowSlowProxies?: boolean;
}
```

Every group inherits run-wide behavior steps and privacy policy unless a later milestone explicitly introduces per-group behavior scripts. This keeps v0.8 focused.

Examples:

```text
savevidly.xyz
  Desktop / Chromium     instances 5   duration 35s   Rotating Pool
  Android / Chrome       instances 6   duration 50s   Rotating Pool
  iPhone 13 / Safari     instances 3   duration 40s   Rotating Pool

example.com
  Desktop / Firefox      instances 2   duration 60s   Static Pool
```

## 1.3 Work units

The scheduler expands target plans into immutable `QaWorkUnit` objects.

```ts
export interface QaWorkUnit {
  workId: string;
  targetId: string;
  targetIndex: number;
  targetUrl: string;
  groupId: string;
  groupIndex: number;
  instanceIndex: number;
  executionKind: QaExecutionKind;
  browser: QaLaunchGroup['browser'];
  deviceProfile?: string;
  androidAvdName?: string;
  realIos?: RealIosCapabilitySelection;
  orientation?: 'portrait' | 'landscape';
  locale?: string;
  timezoneId?: string;
  sessionDurationSeconds: number;
  proxySource: ProxySource;
  allowSlowProxies: boolean;
}
```

`workId` must be stable and collision-free within the run, for example:

```text
target-1-group-2-instance-4
```

Every runtime event, screenshot, proxy reservation, timer, and cleanup record carries `workId`.

# 2. Independent session lifecycle

Each work unit gets its own `SessionLifetimeController` created only after that work unit's browser context exists.

Its countdown starts when that work unit's context starts. It never resets because of:

- navigation;
- redirects;
- new tabs;
- popups;
- user-created tabs;
- Smart Interaction actions;
- returning to the original target.

When the work-unit timer expires, `context.close()` closes every tab/window belonging to that context and only that context. Other work units continue until their own independent deadlines.

Example:

```text
A / Chromium #1 starts 10:00:00, 30s -> closes 10:00:30
B / iPhone #1  starts 10:00:06, 45s -> closes 10:00:51
C / Firefox #2 starts 10:00:12, 20s -> closes 10:00:32
```

There is no shared target timer and no run-wide deadline.

`STOP QA TEST` remains run-wide: abort all active work units, close all active browser contexts / supported emulator sessions, release all reservations, and prevent queued work units from starting.

# 3. Device execution types

## 3.1 Desktop

Supported browsers:

- Chromium
- Firefox
- WebKit

Each instance launches a separate browser context and obtains a separate proxy allocation when using a pool.

## 3.2 Android mobile emulation

Add a scalable Playwright Chromium-based Android mobile emulation mode separate from Android AVD.

v0.8 ships a small curated profile registry rather than hundreds of device definitions. Initial profiles:

- Pixel 7
- Pixel 5
- Galaxy S23-style viewport profile

The implementation may use Playwright's bundled device descriptors where available and project-owned fallback descriptors for stable names.

Browser is Chrome/Chromium Android only. Each emulated instance has its own browser context, timer, proxy allocation, route verification, and storage isolation.

This is the mode intended for configurations such as `6 mobile` instances.

## 3.3 Android AVD

Existing real Android emulator support remains available as a separate execution kind.

AVD constraints:

- One work unit may use a specific AVD at a time.
- Multiple AVD work units require different installed AVD names and sufficient host resources.
- Existing fail-closed proxy limitation remains: pool proxy routing is not advertised for AVD until its emulator network route can be independently verified.

The matrix UI must disable unsupported proxy-source choices rather than silently falling back to direct networking.

## 3.4 Local iPhone/iPad compatibility

Existing Playwright WebKit compatibility mode becomes a launch-group type.

Supported identities:

- Safari iOS compatibility
- Chrome iOS compatibility identity where already supported by the current local compatibility implementation

Each instance uses a separate context and can select an iPhone/iPad profile, orientation, locale, and timezone.

The UI must continue to label this as compatibility/emulation, not a real iPhone.

## 3.5 Real iOS provider

Existing Real iOS provider support remains separate and retains provider capability restrictions. Do not claim local parallelism that the provider does not support.

Smart Interaction remains unavailable for Real iOS in v0.8 unless the provider service receives equivalent tested interaction support in the implementation plan. The matrix UI must expose the limitation clearly.

# 4. Proxy isolation and route verification

Proxy allocation moves from run-level assumptions to the work-unit boundary.

For every work unit using `rotating` or `static`:

1. request a reservation with reservation key `${runId}:${workId}`;
2. launch that work unit with only that reservation;
3. verify the observed proxy route inside that exact browser context before target navigation;
4. run the QA behavior;
5. re-verify route after interaction when there is enough session time;
6. release that exact reservation during cleanup regardless of success, failure, STOP, or timer expiry.

No proxy credentials are exposed to the renderer.

For rotating providers, each work unit performs a fresh pool allocation. The application must not promise that every observed public IP is unique, because a provider may legitimately return the same exit IP more than once. OrbitQA reports the actual observed exit IP per work unit.

For manual proxy mode, multiple work units intentionally use the same manually configured endpoint because there is no pool from which to allocate distinct records.

Direct fallback remains fail-closed for modes whose network path can be verified.

# 5. Scroll Surface Driver

The current Smart Interaction relies too heavily on window scrolling. v0.8 introduces `electron/scroll-surface-driver.cjs`.

## 5.1 Purpose

Find the scroll surface that actually moves visible page content and drive it in deterministic, observable increments.

## 5.2 Surface discovery

Before scrolling, inspect the page for candidates:

- `document.scrollingElement`;
- `html` / `body` when they actually overflow;
- visible elements with `overflow-y: auto|scroll|overlay` and scroll height materially larger than client height;
- large viewport-covering app shells whose nested content owns scrolling.

Rank candidates by:

1. visible area;
2. scrollable distance;
3. viewport coverage;
4. current hit-testing relevance near viewport center.

Verify a candidate by applying one small scroll delta and measuring whether its `scrollTop` or the window offset changes. Restore the original position after discovery when needed.

## 5.3 Scroll behavior

Scrolling is deterministic QA pacing, not anti-detection behavior.

- initial page observation pause: 0.8-1.5 seconds, bounded by remaining session time;
- incremental movement: approximately 80-180 CSS pixels per step;
- pause between steps: approximately 90-220ms;
- after every few increments, invoke the blocker resolver;
- continue until within a small threshold of the bottom or session time becomes too low;
- pause briefly at bottom;
- return upward in the same controlled way;
- stop near an interactive region rather than always forcing exact scroll position 0 if an input/action pair was discovered there.

Tests use deterministic injected timing values; production may use fixed values chosen from the allowed range by a non-stealth pacing policy. No fingerprint or anti-bot randomization is added.

# 6. Blocking Surface Resolver v2

The resolver must stop guessing based only on `Close` selectors.

## 6.1 Detection

At each checkpoint inspect the topmost hit-tested DOM around multiple viewport sample points. A candidate blocking surface is a visible element/frame/backdrop that materially occludes the underlying page through one or more of:

- fixed/sticky positioning;
- high stacking order relative to underlying content;
- large viewport coverage;
- modal/dialog semantics;
- pointer-event interception;
- a backdrop covering the page;
- a child frame occupying a blocking region.

## 6.2 Safe dismissal order

For a confirmed blocker, try in this order:

1. explicit close control inside the blocker;
2. explicit close control associated with the blocker but visually outside its card;
3. small upper-right close-icon candidate whose hit target belongs to the blocker;
4. safe modal backdrop owned by that blocker;
5. Escape key when modal semantics indicate it is appropriate.

Never click an arbitrary blank coordinate merely because the page is blocked.

## 6.3 Repeated blockers

The resolver runs:

- after initial observation;
- during scrolling;
- before input discovery;
- before typing;
- before primary action click;
- immediately after a click;
- while waiting for the remainder of a session when Smart Interaction has finished.

If the blocker reappears, it may be dismissed again.

## 6.4 Popups created by a dismissal

When a safe blocker-dismiss action itself opens a new page/tab:

- allow it to reach `domcontentloaded`, `load`, or a bounded timeout;
- close that popup;
- restore the original work-unit page if still available;
- continue resolving blockers.

This cleanup is specific to blocker-dismiss side effects.

Other tabs/windows created manually or by normal website interaction remain members of the same work-unit context and therefore remain governed by that work unit's timer. At deadline, the whole context closes them all.

## 6.5 Human verification

If the visible blocking surface is a genuine CAPTCHA, Turnstile, reCAPTCHA, hCaptcha, or comparable human-verification challenge and there is no independent safe dismissal:

- do not click the verification control;
- emit `Human verification requires manual action`;
- continue observing the visible browser until the user solves it, the work-unit timer expires, or STOP is pressed;
- if the challenge disappears, resume Smart Interaction automatically.

# 7. Smart Interaction v2

Smart Interaction becomes an orchestrator over the scroll driver and blocker resolver.

## 7.1 Flow

```text
observe page
-> resolve blocker
-> discover real scroll surface
-> browse downward in increments
-> repeatedly resolve blockers
-> pause near bottom
-> browse upward
-> resolve blockers
-> discover safe visible inputs and actions
-> choose contextual input/action pair when present
-> type progressively
-> resolve blocker again
-> click the associated website action
-> observe result/navigation/download/new page
-> continue blocker checks until interaction phase completes
-> route re-verification when applicable
-> remain alive until that work unit's independent timer expires
```

## 7.2 Input discovery

Eligible examples:

- search fields;
- generic text fields;
- URL fields used by a page tool;
- textareas.

Excluded:

- password;
- OTP / verification code;
- payment/card/bank/account-number;
- file upload unless explicitly requested;
- hidden/disabled/read-only fields;
- login credential forms when the run is not explicitly configured for authenticated testing.

## 7.3 Action discovery

Prioritize an action in the same form, card, or nearby DOM container as the chosen input.

Safe intent labels include, when context supports them:

- Search
- Submit
- Go
- Download
- Copy
- Refresh
- Load more
- Next
- Play
- View
- Send
- Apply

Do not blindly click the first matching word on the page. Score actions by association with the selected input and by being outside detected promotional/ad surfaces.

Excluded action intents include:

- Buy / Checkout / Pay / Subscribe with payment;
- Delete / Remove / Destroy;
- Install / Update software;
- Allow browser permissions;
- CAPTCHA / human verification;
- ad/sponsored CTA where promotional context is detected.

## 7.4 Typing and action result

Type progressively into the selected safe field. After typing, resolve blockers again before attempting the associated action.

If the click opens a normal result tab/window, it remains part of the work-unit context and shares that work unit's timer. Smart Interaction may return focus to the original page only when needed for remaining scripted actions; it must not reset the timer.

Downloads are allowed only as an interaction result from a safe page action. The runner records the download event/path when supported and must not execute downloaded content.

# 8. Scheduler

Introduce `electron/work-unit-scheduler.cjs` so expansion and scheduling are not embedded in the browser runner.

Responsibilities:

- expand target plans and launch groups into `QaWorkUnit[]`;
- validate total work-unit count;
- enforce global concurrency 1-5;
- preserve FIFO queue order by target, group, instance unless later policy changes;
- stop dequeuing immediately when the run abort signal fires;
- keep work-unit identity stable in logs and summaries.

Resource constraints are validated before launch:

- the same Android AVD cannot run two work units concurrently;
- unsupported device/browser combinations are rejected;
- unsupported proxy/device combinations are rejected explicitly.

# 10. Request and IPC compatibility

## 10.1 New request

```ts
export interface QaRunRequestV2 {
  targets: QaTargetPlan[];
  concurrency: number;
  headless: boolean;
  steps: QaStep[];
  privacy: PrivacyRunSettings;
}
```

The renderer sends only V2 after the Test Runs migration.

The backend may keep a temporary compatibility normalizer for existing V1 unit tests or internal callers, but V1 is not surfaced in the UI. The compatibility layer must translate one shared V1 configuration into one launch group per URL and be explicitly marked transitional.

## 10.2 IPC

Keep the existing start/stop IPC surface where possible:

- `qa:start`
- `qa:stop`
- QA event channel

No new IPC channel is required solely for the matrix. The request/event payloads gain work-unit metadata.

Secrets never move into renderer state.

# 11. Events, diagnostics, screenshots, and summaries

Every session-level event includes:

- `workId`
- `targetId`
- `groupId`
- `targetUrl`
- device label
- browser label
- instance index

Screenshot filenames include `workId`.

Privacy diagnostics and route diagnostics are stored/emitted per work unit rather than as one ambiguous run-level report.

Run summary adds:

```ts
summary: {
  total: number;
  completed: number;
  failed: number;
  cancelled: number;
  incomplete: number;
  durationMs: number;
}
```

A work unit that reaches its configured session deadline normally after successful QA behavior is `completed`, not failed. A unit whose deadline expires before mandatory pre-navigation privacy/proxy verification or before required behavior begins is `incomplete` with a reason.

---

# 12. Cleanup invariants

For every work unit, cleanup uses `finally` semantics.

It must attempt, independently:

1. context/browser cleanup;
2. Android/remote-session cleanup where applicable;
3. proxy reservation release;
4. lifetime-controller cleanup;
5. final event emission.

A secondary cleanup error must not erase the primary failure, but it must be logged after credential redaction.

STOP must be idempotent. Repeated STOP clicks cannot double-release a proxy or double-delete a remote session.

---

# 13. Error handling

Validation errors identify the target/group where possible:

```text
Target 2, group 1: Firefox is not available for Android mobile emulation
Target 1, group 3: choose an iPhone/iPad profile
Target 4: invalid target URL
Total work units cannot exceed 50
```

Runtime errors include `workId` and preserve credential redaction.

No unsupported configuration silently downgrades to desktop, direct connection, another browser, or another device.

# 16. Migration strategy

Implementation proceeds in this order so every stage is testable:

1. introduce V2 matrix types/validators without changing runner behavior;
2. add scheduler expansion tests;
3. add Android mobile emulation profiles;
4. migrate runner to work-unit configuration and independent proxy/timer lifecycle;
5. add scroll-surface driver;
6. upgrade Smart Interaction and blocking resolver integration;
7. migrate Test Runs UI to target/device matrix;
8. remove/retire shared-run UI assumptions;
9. run all automated suites and browser-health checks;
10. package only after Windows-side Vitest/build/browser-health are green.

The V1 adapter, if retained, is compatibility code only and must not become the permanent internal model.

# 17. Acceptance criteria

v0.8 is accepted only when all of the following are true:

- A single URL can be configured with multiple independent device/browser groups and instance counts.
- Different URLs may have different device/browser group compositions.
- Every generated instance has its own browser/device lifecycle, timer, logs, screenshots, and proxy allocation.
- One instance reaching its deadline never closes another instance.
- Pool-backed work units allocate/release independently and verify their own route.
- A page whose content scrolls inside a nested container visibly scrolls under Smart Interaction.
- Smart Interaction browses down and up in deterministic incremental steps, repeatedly resolving blockers.
- Safe contextual input/action interactions work without clicking destructive, sensitive, sponsored, or human-verification controls.
- Blockers may reappear and be dismissed repeatedly when a safe dismissal exists.
- New/manual tabs remain governed by the owning work unit's original non-resetting timer.
- Run-wide STOP closes active work units and cancels queued ones.
- Visible desktop runs can show a cursor indicator that moves to the actual QA target and pulses on click; mobile/iPhone compatibility runs show a touch marker instead. The indicator uses `pointer-events:none`, carries no input privileges, and does not modify browser identity or anti-bot surfaces.
- No ad blocker is introduced.
- No CAPTCHA/human-verification bypass is introduced.
- Existing privacy fail-closed behavior and credential redaction remain intact.
- All required automated tests, TypeScript build, and desktop browser-health checks pass before release.

# 18. Visible interaction indicator

## 18.1 Purpose

Visible QA runs should show what OrbitQA is about to interact with. This is an operator-facing visualization only. It must not spoof OS input, alter browser/device fingerprints, or attempt to make automation undetectable.

## 18.2 Desktop cursor

For `desktop` work units in visible-browser mode, inject a non-interactive cursor overlay into each page. The cursor:

- uses `position: fixed` and `pointer-events: none`;
- is ignored by blocker hit-testing and target discovery using a dedicated `data-orbitqa-indicator` attribute;
- moves deterministically to the center of the real target element before click/type actions;
- may animate over a short fixed duration for operator readability;
- shows a short click pulse only when OrbitQA performs a real QA click;
- is reinstalled after navigation when needed;
- is hidden in headless runs and when the run-wide indicator setting is disabled.

The cursor is never used as the source of truth for clicking. Playwright still clicks the resolved target element itself.

## 18.3 Mobile/iPhone touch marker

For `android-emulation`, `android-avd` where supported, and `ios-emulation`, show a circular touch marker rather than a mouse arrow. The marker moves to the actual tap/input target and pulses on tap. It has the same `pointer-events:none` and non-interference guarantees as the desktop cursor.

Real iOS provider runs only show an indicator if the provider path can inject it without changing provider capabilities; otherwise the UI labels the indicator unavailable for that group.

## 18.4 Run-wide setting

`QaRunRequestV2` adds:

```ts
interactionIndicator: boolean;
```

The Test Runs UI exposes `Show interaction pointer` as a run-wide switch. Default is `true` for visible-browser runs and ignored when the browser is headless.

## 18.5 Integration

`electron/interaction-indicator.cjs` exports:

```js
installInteractionIndicator(page, { mode })
moveInteractionIndicator(page, target, { mode })
pulseInteractionIndicator(page, { mode })
removeInteractionIndicator(page)
```

`mode` is `'cursor' | 'touch'`. Smart Interaction and manual click/type steps call `moveInteractionIndicator()` immediately before their real interaction. Scroll visualization may keep the indicator stationary; the indicator must not generate synthetic page input.

## 18.6 Safety and non-interference

The indicator DOM is visual-only and must:

- never receive pointer events;
- never be included as a Smart Interaction candidate;
- never be treated as a blocker;
- never change user-agent, navigator fields, viewport, WebRTC, canvas/WebGL, or browser fingerprints;
- never attempt bot-detection evasion;
- never solve or click CAPTCHA / human-verification controls.
