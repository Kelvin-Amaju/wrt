# OrbitQA Real iOS Device Connector Design

## Goal

Add a real-iOS testing path to OrbitQA that can run authorized browser QA against an actual iPhone/iPad through a remote device provider, while keeping the current Windows WebKit mode as a clearly labeled local compatibility mode.

## Product Split

OrbitQA will expose two separate iOS paths:

1. **Local iOS Compatibility**
   - Runs Playwright WebKit locally on Windows.
   - Keeps current mobile viewport, DPR, user-agent, locale, timezone, orientation, and WebRTC exposure diagnostics.
   - Clearly labels navigator/platform/touch mismatches as warnings.
   - Never claims to be a real iPhone or real Safari runtime.

2. **Real iOS Device**
   - Runs against an actual iPhone/iPad supplied by a remote device provider.
   - Uses the provider's supported automation endpoint for Safari and, where supported, Chrome iOS.
   - Receives real device/browser telemetry from the provider session rather than spoofing host values.
   - Captures provider session status, screenshots, test logs, duration, browser identity, device model, OS version, and network/WebRTC diagnostics available inside the page.

## V1 Provider Architecture

The first implementation will use a provider-adapter interface instead of hard-coding OrbitQA to one vendor.

```text
OrbitQA UI
   |
Electron IPC
   |
RealIosService
   |
ProviderAdapter
   |-- createSession()
   |-- navigate()
   |-- performStep()
   |-- getDiagnostics()
   |-- captureScreenshot()
   |-- closeSession()
   v
Remote real-device provider
   v
Actual iPhone / iPad
```

V1 will ship with a **Generic WebDriver/Appium-compatible adapter**. This allows OrbitQA to connect to a provider that exposes a remote WebDriver endpoint and capabilities. Vendor-specific convenience presets can be added later without changing the rest of the app.

## Provider Configuration

A new Settings section called **Real iOS Provider** will contain:

- Provider name: free-text label for the connection.
- Remote WebDriver URL: HTTPS endpoint only.
- Username: optional, depending on provider.
- Access key/token: encrypted at rest using Electron `safeStorage` when available.
- Default iOS device model: text/capability field.
- Default iOS version: text/capability field.
- Default browser: `safari` or `chrome` when the provider supports it.
- Connection test button.

Secrets must never be rendered back in full after saving. The UI shows only whether credentials are saved.

## Test Runs Integration

`Target device` will contain:

- Desktop Browser
- Android Virtual Device
- Local iOS Compatibility
- Real iOS Device

When **Real iOS Device** is selected, Test Runs will show:

- Provider connection status.
- Device model.
- iOS version.
- Browser: Safari or Chrome iOS, based on provider capability.
- Session count: fixed to `1` in V1.
- Concurrency: fixed to `1` in V1.
- Existing visual behavior steps: Wait, Scroll, Click, Type, Screenshot.
- Start Real iOS Test button.

If provider settings are missing or the connection test fails, Start remains disabled and the UI explains why.

## Real Device Session Data Flow

1. Renderer validates the QA request.
2. Electron main process receives the request over a dedicated IPC channel.
3. `RealIosService` loads the saved provider configuration.
4. The provider adapter creates one remote device session.
5. OrbitQA navigates to the authorized target URL.
6. Existing behavior steps are translated into WebDriver actions.
7. OrbitQA gathers page-observable diagnostics.
8. OrbitQA captures the final screenshot.
9. OrbitQA closes the remote session in `finally`, including on step failure.
10. The renderer receives structured logs and a final result.

## Page-Observable Diagnostics

For a real iOS run, OrbitQA will report values the page can actually observe:

- `navigator.userAgent`
- `navigator.platform`
- `navigator.maxTouchPoints`
- viewport width/height
- screen width/height
- `devicePixelRatio`
- locale
- timezone
- WebRTC availability
- literal IP candidates exposed by ICE gathering, if any

OrbitQA will report these values as observed. It will not modify Canvas, WebGL, AudioContext, ClientRects, hardware-concurrency, WebRTC identity, or other fingerprint surfaces to evade detection.

## WebRTC Handling

The feature is diagnostic, not spoofing.

- OrbitQA checks whether WebRTC is present.
- OrbitQA collects ICE candidates generated by the page context.
- OrbitQA flags literal public/private IP candidates when observed.
- OrbitQA does not inject fake candidates, rewrite candidates, or forge network identity.

## Browser Support

### Safari iOS

Primary real-iOS browser for V1. The provider must expose Safari automation through its WebDriver/Appium-compatible service.

### Chrome iOS

Shown only when the configured provider explicitly supports automating Chrome on the selected iOS device. OrbitQA must not claim Chrome iOS support when the provider cannot launch it.

## Local iOS Compatibility Changes

The existing local mode will be renamed throughout the UI from **iOS Browser QA** to **Local iOS Compatibility**.

The mode continues to:

- run WebKit locally on Windows;
- show compatibility profiles for iPhone/iPad;
- show warnings for `Win32`, missing touch points, or other host-runtime mismatches;
- provide WebRTC exposure diagnostics;
- state clearly that it is not Apple's iOS Simulator.

## Components

### Renderer

- `src/pages/Run.tsx`
  - Add the Real iOS Device target mode.
  - Render provider/device controls.
  - Display live remote-session state and diagnostics.

- `src/pages/Settings.tsx`
  - Add Real iOS Provider settings form.
  - Add Save and Test Connection actions.

- `src/pages/DeviceProfiles.tsx`
  - Rename local iOS mode to Local iOS Compatibility.
  - Add a Real iOS Device card explaining provider-backed physical devices.

- `src/shared/testRun.ts`
  - Add `real-ios` target-device validation.
  - Enforce one session and one concurrent remote device in V1.

- `src/shared/realIos.ts`
  - Shared types for provider configuration, capability selection, connection-test responses, diagnostics, and session results.

### Electron Main Process

- `electron/real-ios-service.cjs`
  - Load/save encrypted provider configuration.
  - Validate endpoint protocol and required settings.
  - Create/close sessions through the adapter.
  - Execute steps and emit logs.

- `electron/real-ios-provider.cjs`
  - Generic WebDriver/Appium-compatible HTTP adapter.
  - No vendor-specific UI assumptions.

- `electron/main.cjs`
  - Add IPC handlers for provider settings, connection testing, device run start, and run events.

- `electron/preload.cjs`
  - Expose only narrow typed methods to the renderer.

## Security

- Provider endpoint must use HTTPS except `http://127.0.0.1` or `http://localhost` for local development.
- Access tokens are encrypted with Electron `safeStorage` when supported.
- Tokens are never sent to the renderer after storage.
- Logs must redact credentials and query parameters named `token`, `key`, `secret`, `password`, or `accessKey`.
- Remote sessions are always terminated in cleanup logic.
- Camera and microphone permissions are not granted automatically.
- The feature is for authorized QA targets and does not include anti-detection fingerprint spoofing.

## Error Handling

OrbitQA will distinguish:

- Provider configuration missing.
- Provider authentication rejected.
- Provider unreachable/timeout.
- Requested iOS device unavailable.
- Requested browser unsupported.
- Remote session creation timeout.
- Navigation failure.
- Individual behavior-step failure.
- Screenshot failure.
- Session-cleanup failure.

The UI will preserve the primary failure while also logging cleanup errors separately.

## Performance

- Real iOS V1 permits one remote session at a time.
- No provider polling occurs when Real iOS Device is not selected.
- Connection tests occur only on user action.
- The local Electron app remains lightweight when no test is running.

## Testing

### Unit tests

- `real-ios` request validation.
- Endpoint protocol validation.
- Secret redaction.
- Provider response normalization.
- Browser capability gating.
- Session cleanup on success and failure.

### Renderer tests

- Real iOS controls appear only for the Real iOS target.
- Start is disabled without valid provider settings.
- Chrome iOS is hidden/disabled when unsupported.
- Local mode is labeled Local iOS Compatibility.
- Diagnostics render observed values without converting warnings into fake passes.

### Service tests

Use a local fake WebDriver HTTP server in tests to verify:

- connection test;
- session creation;
- navigation command;
- step command translation;
- screenshot retrieval;
- diagnostics script execution;
- session deletion in `finally`.

No paid provider account is required for automated tests.

## Acceptance Criteria

The feature is ready when:

1. Existing Desktop, Android, and Local iOS Compatibility tests continue to pass.
2. Provider settings can be saved without exposing the stored access key back to the renderer.
3. A fake WebDriver server passes the full automated real-iOS service test flow.
4. Real iOS Test Runs are blocked until provider configuration validates.
5. Safari can be selected for a provider that reports Safari support.
6. Chrome iOS appears only when the provider reports Chrome support.
7. Remote sessions are closed after both successful and failed runs.
8. The results panel shows real page-observed diagnostics and WebRTC exposure without spoofing fingerprint values.
9. Local iOS Compatibility remains clearly labeled as Windows WebKit compatibility testing, not a real iPhone.
